# Сборка и запуск на Android

Приложение упаковывается в APK через [buildozer](https://buildozer.readthedocs.io/)
и python-for-android. Buildozer не работает на Windows напрямую, поэтому сборка
идёт в Linux-контейнере — локально через Docker или в GitHub Actions.

---

## Вариант 1: локальная сборка (Docker)

Нужен установленный и **запущенный** Docker Desktop.

```
build_android.bat
```

Скрипт соберёт образ из `Dockerfile` и запустит в нём `buildozer android debug`.
Готовый APK окажется в `bin/`, полный лог сборки — в `build.log`.

| Команда | Что делает |
|---------|------------|
| `build_android.bat` | Инкрементальная сборка, кэш `.buildozer/` сохраняется |
| `build_android.bat clean` | Стирает `.buildozer/` и `bin/`, следующая сборка — полная |

**Первая сборка занимает 40–90 минут** и скачивает Android SDK/NDK (~3 ГБ).
Последующие идут заметно быстрее за счёт кэша — поэтому скрипт, в отличие от
CI, не удаляет `.buildozer/` перед каждым запуском.

---

## Вариант 2: сборка в GitHub Actions

Workflow `.github/workflows/build.yml` запускается вручную (Actions →
Build Android APK → Run workflow) или автоматически при push в `main`.
APK и лог сборки скачиваются со страницы запуска как артефакты
`musictrainer-apk` и `build-log`.

Удобно, когда локально нет Docker или не хочется занимать машину на час.

## Установка на телефон

APK собирается debug-сборкой и подписан отладочным ключом — в Google Play
такой не опубликовать, но поставить на свой телефон можно.

### Через USB (adb)

1. На телефоне: Настройки → О телефоне → семь раз нажать «Номер сборки»,
   затем в Настройках → Для разработчиков включить **Отладка по USB**.
2. Подключить телефон кабелем, разрешить отладку в появившемся запросе.
3. Установить:

```
adb install -r bin\musictrainer-17.5-arm64-v8a-debug.apk
```

Точное имя файла смотрите в `bin/` — оно зависит от версии и архитектуры.

### Без кабеля

Скопировать APK на телефон любым способом (облако, мессенджер, флешка)
и открыть его файловым менеджером. Android попросит разрешить установку
из неизвестных источников.

## Совместимость

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| `android.archs` | `arm64-v8a, armeabi-v7a` | Покрывает практически все актуальные телефоны |
| `android.minapi` | 24 | Android 7.0 и новее |
| `android.api` | 31 | Целевой уровень API |

**OnePlus 9RT** — Snapdragon 888, архитектура `arm64-v8a`, Android 11 и новее.
Под текущие настройки подходит; ставить нужно `arm64-v8a`-вариант APK.

Про публикацию в Google Play: там требуется targetSdk не ниже 34, то есть
`android.api` придётся поднимать, а сборку — подписывать релизным ключом
вместо отладочного.

## Известные риски

Сборка APK — незакрытая задача проекта (см. `docs/CONTEXT.md`), и в конфигурации
есть места, которые стоит держать в голове при разборе ошибок.

### Версия pygame

Рецепт pygame в python-for-android жёстко собирает **2.1.0**. Раньше в
`requirements` стояло `pygame==2.6.1` — при таком запросе p4a качает исходники
2.6.1, но собирает их логикой рецепта, написанной под 2.1.0. Сейчас версия
снята, чтобы использовалась проверенная рецептом.

Следствие: **на Android поедет pygame 2.1.0, а на десктопе стоит 2.6.1.**
Расхождение версий звукового движка между платформами — первое, на что стоит
смотреть, если звук ведёт себя на телефоне иначе.

Сам рецепт помечен авторами как частично непротестированный: часть зависимостей
(freetype, portmidi, libjpeg) в сборку не входит.

### Версия Kivy

Локальный рецепт `p4a-recipes/kivy/` собирает Kivy **2.1.0** и патчит его под
GLES2, тогда как на десктопе работает **2.3.1**. Патчи в рецепте написаны под
структуру исходников 2.1.0 — просто поднять версию не получится, придётся
проверять, что каждая замена в `build_arch()` всё ещё находит свою цель.

### Версия NDK

В `buildozer.spec` указан `android.ndk = 28c`, тогда как buildozer 1.6.0 и
python-for-android 2024.01.21 из `Dockerfile` тестировались с NDK 25b.
Если сборка падает на этапе компиляции нативного кода — это первый кандидат
на понижение.

### Кастомный hostpython3

`p4a-recipes/hostpython3/` подменяет штатную сборку hostpython3 на системный
`/usr/local/bin/python3.10` из образа. Это обход, а не штатный путь p4a:
при обновлении buildozer или p4a рецепт может разойтись с их внутренним API.

Конфигурация разобрана статически: пути под новую структуру `src/` поправлены,
из `buildozer.spec` убран несуществующий ключ `hostpython3`, снята конфликтующая

**Сама сборка APK не запускалась** — на машине не был запущен движок Docker,

и документации p4a, а не воспроизведением сборки.

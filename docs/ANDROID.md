# Сборка и запуск на Android

Приложение упаковывается в APK через [buildozer](https://buildozer.readthedocs.io/)
и python-for-android. Buildozer не работает на Windows напрямую, поэтому сборка
идёт в Linux-контейнере — локально через Docker или в GitHub Actions.

---

## Вариант 1: локальная сборка (Docker)

Нужен установленный и **запущенный** Docker Desktop.

```
build_android.bat
```

Скрипт соберёт образ из `Dockerfile` и запустит в нём `buildozer android debug`.
Готовый APK окажется в `bin/`, полный лог сборки — в `build.log`.

| Команда | Что делает |
|---------|------------|
| `build_android.bat` | Инкрементальная сборка, кэш `.buildozer/` сохраняется |
| `build_android.bat clean` | Стирает `.buildozer/` и `bin/`, следующая сборка — полная |

**Первая сборка занимает 40–90 минут** и скачивает Android SDK/NDK (~3 ГБ).
Последующие идут заметно быстрее за счёт кэша — поэтому скрипт, в отличие от
CI, не удаляет `.buildozer/` перед каждым запуском.

---

## Вариант 2: сборка в GitHub Actions

Workflow `.github/workflows/build.yml` запускается вручную (Actions →
Build Android APK → Run workflow) или автоматически при push в `main`.
APK и лог сборки скачиваются со страницы запуска как артефакты
`musictrainer-apk` и `build-log`.

Удобно, когда локально нет Docker или не хочется занимать машину на час.

## Установка на телефон

APK собирается debug-сборкой и подписан отладочным ключом — в Google Play
такой не опубликовать, но поставить на свой телефон можно.

### Через USB (adb)

1. На телефоне: Настройки → О телефоне → семь раз нажать «Номер сборки»,
   затем в Настройках → Для разработчиков включить **Отладка по USB**.
2. Подключить телефон кабелем, разрешить отладку в появившемся запросе.
3. Установить:

```
adb install -r bin\musictrainer-17.5-arm64-v8a-debug.apk
```

Точное имя файла смотрите в `bin/` — оно зависит от версии и архитектуры.

### Без кабеля

Скопировать APK на телефон любым способом (облако, мессенджер, флешка)
и открыть его файловым менеджером. Android попросит разрешить установку
из неизвестных источников.

## Совместимость

| Параметр | Значение | Комментарий |
|----------|----------|-------------|
| `android.archs` | `arm64-v8a, armeabi-v7a` | Покрывает практически все актуальные телефоны |
| `android.minapi` | 24 | Android 7.0 и новее |
| `android.api` | 31 | Целевой уровень API |

**OnePlus 9RT** — Snapdragon 888, архитектура `arm64-v8a`, Android 11 и новее.
Под текущие настройки подходит; ставить нужно `arm64-v8a`-вариант APK.

Про публикацию в Google Play: там требуется targetSdk не ниже 34, то есть
`android.api` придётся поднимать, а сборку — подписывать релизным ключом
вместо отладочного.

## История сборки: что ломалось и почему

Раздел стоит прочитать перед тем, как менять версии в `buildozer.spec` или
`Dockerfile` — большинство «очевидных» правок здесь уже приводили к отказу.

### buildozer игнорирует пин p4a из Dockerfile

Главная ловушка. В `Dockerfile` стоял `python-for-android==2024.01.21`, но
buildozer **не использует установленный пакет** — он клонирует p4a сам:

```
git clone -b master --single-branch https://github.com/kivy/python-for-android.git
```

Ветку задаёт ключ `p4a.branch` в `buildozer.spec`, по умолчанию `master`.
То есть версия из `Dockerfile` не влияла ни на что, и сборка каждый раз
получала свежий p4a. Если понадобится закрепить версию — это делается
через `p4a.branch`, а не через pip.

### numpy требует Python >= 3.11

Прямое следствие предыдущего пункта. Актуальный p4a собирает numpy 2.3.0,
а начиная с 1.26 numpy собирается через `meson-python`, которому нужен
Python 3.11 и новее. При этом образ был на Python 3.10, а кастомный рецепт
`p4a-recipes/hostpython3/` жёстко подставлял `/usr/local/bin/python3.10`.
Сборка падала так:

```
meson-python: error: The package requires Python version >=3.11, running on 3.10.21
ERROR Backend subprocess exited when trying to invoke build_wheel
```

Решение: образ переведён на `python:3.12-slim`, пин `python3==3.10.0`
из требований убран, кастомный рецепт `hostpython3` удалён — p4a собирает
hostpython сам.

### Удалённые кастомные рецепты

Папка `p4a-recipes/` содержала два обхода, оба удалены (остаются в истории git):

- **`hostpython3`** — подменял сборку hostpython на системный Python 3.10.
  Именно он фиксировал версию, из-за которой падал numpy.
- **`kivy`** — собирал Kivy 2.1.0 и патчил `gl_redirect.h`, подменяя заголовки
  OpenGL на GLES2. Актуальный рецепт kivy делает это сам: он пинует
  **2.3.1** (ровно ту версию, что работает на десктопе) и настраивает SDL2
  и графику под Android без вмешательства.

### Падение сборки маскировалось как успех

В workflow команда была записана как `buildozer ... | tee build.log`.
Код возврата конвейера в bash — это код последней команды, то есть `tee`,
который всегда успешен. Из-за этого шаг «Build APK» помечался зелёным даже
когда buildozer падал, а сборка обрывалась только на шаге «Upload APK»
с сообщением, что в `bin/` нет файлов.

Исправлено: добавлен `set -o pipefail`, а `su` запускается с `-s /bin/bash`
(в dash, который `su` берёт по умолчанию, `pipefail` не поддерживается).
Плюс добавлен шаг, печатающий хвост `build.log` прямо в вывод при падении.

### pygame не собирается ни под 3.14, ни в версии из рецепта

После перехода на актуальный p4a numpy собрался, но сборка упала на pygame:

```
src_c/_sdl2/sdl2.c:211:12: fatal error: 'longintrepr.h' file not found
```

Здесь сошлись два ограничения навстречу друг другу:

- Рецепт p4a пинует pygame **2.1.0** (2021). Он включает `longintrepr.h`,
  который убрали из публичного API CPython в 3.11 — то есть 2.1.0 не
  собирается ни под какой современный Python.
- Актуальный pygame — **2.6.1**, но его верхняя граница 3.12/3.13.
  Под Python 3.14, который p4a собирает по умолчанию, pygame не работает
  (в трекере pygame открыт issue об этом).

Снизу при этом подпирает numpy: `meson-python` требует Python >= 3.11.
Рабочее окно — **3.11–3.13**, поэтому в требованиях закреплены
`python3==3.12.11` и `pygame==2.6.1`.

Вывод на будущее: **пин pygame снимать нельзя.** Версия из рецепта
заведомо нерабочая, и «упрощение» требований возвращает эту ошибку.

### Локальная сборка упирается в скорость сети

При медленном канале локальная сборка непрактична: загрузка Android SDK/NDK
и исходников — это несколько гигабайт. На замере 165 кБ/с одна только
установка пакетов в образ заняла час, а контейнер затем был убит по OOM
(код 137). На раннере GitHub те же шаги проходят за минуты.

## Текущий целевой стек

| Компонент | Версия | Откуда берётся |
|-----------|--------|----------------|
| host Python | 3.12 | `Dockerfile` |
| buildozer | 1.6.0 | `Dockerfile` |
| python-for-android | master | клонируется buildozer'ом |
| target Python | 3.12.11 | пин в `buildozer.spec` |
| Kivy | 2.3.1 | рецепт p4a — совпадает с десктопом |
| pygame | 2.6.1 | пин в `buildozer.spec` — как на десктопе |
| numpy | 2.3.0 | рецепт p4a |
| NDK | r28c | `buildozer.spec` |

Версии pygame и Kivy теперь совпадают с десктопными — расхождения движков
между платформами нет. Но рецепт pygame помечен авторами p4a как частично
непротестированный: freetype, portmidi и libjpeg в сборку не входят. Если
звук на телефоне поведёт себя не так, как на компьютере, смотреть надо туда.

## Что проверено, а что нет

**Собирается под arm64-v8a:** hostpython3, jpeg, libffi, openssl, png, sqlite3,
SDL2 со всеми модулями (image, mixer, ttf), Python, pyjnius, setuptools, android
и **numpy** — в логе `Successfully built numpy-2.3.0-cp314-cp314-aarch64_linux_android.whl`.
Структура `src/` для сборки корректна.

**Не проверено:** компиляция pygame и Kivy под ARM — до них сборка пока не
доходила. Соответственно неизвестно, собирается ли APK целиком, ставится ли
он на телефон и работает ли в нём звук.
